## 1. Found and fixed: a documentation/code mismatch in reproducibility logging

`docs/PLAN.md` Section F explicitly claimed "every run writes full
hyperparameters + seed + git commit hash into its results.json entry." This
was not true. Per-run records had strategy/seed/steps/batch size/grad-accum
steps/learning rate, but were missing: the git commit hash, dataset
name/config, max sequence length, tokenization/eval sample counts, the
optimizer name, the gradient-checkpointing flag, and the exact FakeQuant
quantization scheme (per-channel vs per-tensor, observer type).

Fixed by adding `common.run_metadata()` (with a best-effort
`git_commit_hash()` that degrades to `"unknown"` rather than ever failing a
training run) and wiring it into every result-logging path: `train_qat.py`,
`eval_baseline.py`, `smoothquant_manual.py`. Verified end-to-end with a live
3-step smoke test before trusting it for real runs (see commit `e45a086`).

**This does not require re-running any of the 24 already-completed runs** --
every run in this project used identical hyperparameters from the single
source of truth (`config.py`), which is itself version-controlled, so the
actual experimental settings for old runs remain fully recoverable from git
history even without being stamped inline on each result.

## 2. Found and fixed: a real internal inconsistency in OPT-350M's eval sets (this one DID need action, but not retraining)

While answering the "would old runs need to be re-run" question, checked the
eval-side data directly and found that OPT-350M's own results table was not
internally consistent:

| Configuration | Eval set actually used |
|---|---|
| Control (all 3 seeds) | Full 10,000-example set (ran before the Day 2 eval-speed fix) |
| Weights-only, seed 42 & 1337 | Full 10,000-example set (ditto -- these were the real re-runs after the resumability bug fix, but still before the eval-speed fix landed) |
| Weights-only, seed 2024 | 1,500-example subset (ran right after the eval-speed fix) |
| Activations-only, both (all seeds) | 1,500-example subset |

Pythia-410M was unaffected -- it was trained entirely after the eval-speed
fix landed, so all 12 of its runs consistently used the 1,500-example
subset. This OPT-350M inconsistency happened because the fix landed mid-way
through that model's matrix, and the original resume logic had no way to
know a completed run's *eval set* had changed underneath it, only that a
result existed for that (strategy, seed) pair.

**Fix: `src/reeval_subset_fix.py`, re-evaluation only, no retraining.** Every
run already had a saved FP16 checkpoint. Loaded the 5 affected checkpoints
(`load_trained_checkpoint()`, reused from `eval_downstream.py`) and re-ran
`evaluate_perplexity()` on the same 1,500-example subset used everywhere
else, replacing only the eval-side fields (perplexity, eval time, peak eval
VRAM, token count) while preserving the original training-side fields
(training time, peak training VRAM, quantization error logs) unchanged,
since those were never affected by which eval set was used.

Result: numbers shifted slightly (control mean 21.12 -> 21.02, weights-only
mean 21.18 -> 21.09) but **the qualitative finding is unchanged** -- the
relative gap between weights-only and the control is essentially identical
before and after (~0.3% either way). This is worth stating plainly: the fix
mattered for methodological rigor and for withstanding review scrutiny, not
because the original numbers were meaningfully wrong.

## 3. Infrastructure incident: HuggingFace Hub connectivity failure

First attempt to launch the Qwen2.5-0.5B pipeline failed within seconds --
every HTTP request to `huggingface.co` returned `[Errno 11002] getaddrinfo
failed` (DNS resolution failure), meaning no network connectivity at that
moment. This is notable because it's the *first* time this project has
needed to download Qwen2.5-0.5B's actual model weights (earlier sessions
only cached its tokenizer via `prepare_data.py`), so there was no local
cache to fall back on -- the failure was immediate and total rather than a
partial/degraded run.

Diagnosed with a direct `ping`/`curl` check against `huggingface.co`, which
confirmed connectivity had returned (this was a transient network blip, not
a persistent outage or a firewall/DNS misconfiguration). Retried the
identical command and it proceeded normally. No code changes were needed --
this is logged here because a background pipeline that fails silently and
"completes" in seconds looks identical, from the outside, to one that
finished a full run successfully, which is worth being able to distinguish
at a glance later.

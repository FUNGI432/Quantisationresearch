# Session Report — 2026-08-30 (Day 5 of the v2 expansion)

## 0. Context

Continuation from [`2026-08-29_session-4.md`](2026-08-29_session-4.md). At
the start of this session: Qwen2.5-0.5B's `none`/seed=42 QAT run had been
resumed and was progressing (step 350 -> 400 -> 450 of 500 over the course
of monitoring), still exhibiting the same unresolved slowdown pattern.

## 1. The slowdown escalated past every previous instance, then crossed into "we can't tell if it's stuck"

Tracking the run's checkpoint progress across this session:

| Time | Step | Cumulative train time |
|---|---|---|
| 00:54 | 400/500 | 7.41 hr |
| 03:52 | 450/500 | 10.21 hr |
| ~06:15 (est.) | 500/500 (training complete) | ~13 hr (extrapolated) |
| 12:24 | training resume checkpoint **gone** (deleted -- only happens on real training completion) | -- |
| 13:37 | still no eval result, no final checkpoint | -- |
| 14:00 | still nothing; GPU still 100% utilization, ~5.4-5.8 GB VRAM throughout | -- |

The training-resume checkpoint's deletion is strong evidence training
genuinely reached step 500 around the estimated ~06:15 mark. What followed
was **7+ hours in what should be a ~3-minute evaluation pass**, with GPU
utilization the only available signal, and that signal cannot distinguish
"still making genuine progress" from "stuck in a loop that keeps the GPU
busy without advancing." This is qualitatively different from every prior
occurrence of the slowdown (worst previously seen: ~2 hours, on Pythia's
eval) -- this instance is ~3.5x worse than the previous worst case and, more
importantly, crossed a threshold where "just keep waiting" stopped being an
obviously safe default.

**A related design gap was found while reasoning about whether to
intervene**: the mid-training checkpointing built on Day 3 only covers the
*training* phase. Its resume checkpoint is deleted the moment training
finishes -- meaning if the process is killed during the following eval
phase, there is no way back to the completed training state, and the entire
10+ hour training run would have to be redone from scratch. This made the
"just kill it" option far more costly than it should be, and was flagged
directly rather than discovered by making that mistake.

## 2. Two decision points, both deferred to explicit user choice rather than assumed

1. Whether to keep waiting on the ambiguous multi-hour eval or kill it and
   accept the loss -- kept waiting, given the real cost of guessing wrong
   in either direction (wasted time vs. a fully-redone 10+ hour run).
2. Given the core complaint -- "GPU-busy is not a definitive signal, and we
   can't tell if a stoppage is happening" -- a set of concrete code changes
   was requested rather than continuing to guess from outside the process.

## 3. Code changes: visibility, finer-grained resumability, and closing the eval-checkpoint gap

All changes are in `src/common.py`, `src/train_qat.py`, `src/config.py`,
`src/eval_baseline.py`, `src/smoothquant_manual.py`. Verified via
`py_compile` on all affected files; **NOT yet verified with a real GPU run**
(see §4 for why, and what that means going forward).

**Root cause of the visibility problem, fixed directly**: stdout was
full-buffered by default (Python's normal behavior when stdout isn't a
terminal, e.g. piped to a log file by a background shell) -- meaning
`print()` calls didn't actually appear until the buffer filled or the
process exited. This explains a pattern noticed repeatedly across the whole
project ("Loading weights: 100%" shows, then nothing, then everything
appears at once at completion) that had been worked around by inspecting
checkpoint files directly instead of trusting stdout. Fixed with
`sys.stdout.reconfigure(line_buffering=True)` at the top of every
entry-point script -- prints now flush immediately as they happen.

**Training loop**: now prints every single step (previously every 50),
including per-step wall-clock time and cumulative elapsed time -- a step
that suddenly takes 10x longer than its neighbors is now visible
immediately, not inferred after the fact from a 50-step aggregate.
`config.CHECKPOINT_EVERY_STEPS` lowered from 50 to 10 -- with a single step
sometimes taking minutes (as established this session), 50 was found to be
a dangerously coarse safety margin; checkpoint write overhead (a few GB to
local disk) is negligible relative to any realistic step interval, so this
costs nothing meaningful.

**Eval loop** (`common.evaluate_perplexity`): previously silent from start
to finish, now prints progress every `config.EVAL_CHECKPOINT_EVERY_BATCHES`
(10) batches with a running perplexity estimate and elapsed time. **Eval is
now resumable at the batch level** -- the exact gap identified in §1. A
resume file accumulates `(batch_idx, total_nll, total_tokens,
per_example_nll)` and is loaded on restart to skip already-evaluated
batches (cheap -- no model forward pass needed to skip a batch already
computed) rather than restarting eval from batch 0.

**Ordering fix in `train_qat.py`**: the training-phase resume checkpoint is
now deleted only *after* both eval and results are fully saved, not
immediately after the training loop finishes. Previously, deleting it right
after training meant the only copy of the trained model weights disappeared
before eval had a chance to use it for its own resume path -- if eval then
got killed, there would have been no model to resume evaluating.

## 4. Important caveat: this does NOT help the run currently stuck

The Qwen process that has been running for 14+ hours already has the OLD
code loaded in memory -- these changes take effect only for processes
started after this point. Two consequences:

1. **We still can't see what that specific run is doing right now.**
2. **If it's killed and restarted, the new eval-resume logic has never been
   exercised on a real GPU run** -- unlike the Day 3 training-checkpoint
   feature, which was deliberately tested against a real hard kill before
   being trusted. This one is syntax-verified only, for the same reason
   Day 3's testing wasn't repeated here: doing so requires GPU time, and the
   GPU has been continuously occupied by the run this was written in
   response to.

This means resuming (or restarting) Qwen's matrix after this session ends
carries slightly more first-run risk than usual, and that first resume
should be watched more closely than a routine one, precisely because the
new mechanism it depends on is unverified in practice.

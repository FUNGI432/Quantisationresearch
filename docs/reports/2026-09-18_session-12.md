## 1. Section D: significance testing, actually run for the first time

**Backfill.** `backfill_per_example_nll.py --model opt-350m` and
`--model pythia-410m` (24 runs total) re-evaluated every already-completed
OPT/Pythia checkpoint to produce the per-example NLL arrays needed for a
real paired test. All 24 completed; the script's built-in sanity check
(compare recomputed PPL against the originally stored value) passed
exactly for all of OPT-350M's runs and for `none`/`weights_only` on both
models, but flagged 6 of Pythia-410M's runs (all `activations_only`/`both`)
as exceeding its 1% tolerance -- investigated rather than ignored, see §2.

**Significance testing.** `stats.py` was extended with a
`benjamini_hochberg()` correction and a `full_significance_report()` that
pools every per-seed Wilcoxon test into one corrected family, per the
paper outline's Methodology E requirement (never implemented until now).
Result: **24 per-seed tests ran** (3 models x 3 QAT strategies vs.
control; 3 of the possible 27 triples were skipped -- Qwen
`weights_only`/seed=42 has no per-example data, a previously documented,
unrelated gap from a Day-7 crash-recovery incident). **21 of 24 are
significant after Benjamini-Hochberg correction; the correction did not
overturn a single raw-significant result.** Every `activations_only` and
`both` comparison (18 tests) is significant, most at p<10⁻⁶. The 3
non-significant results are all `weights_only` vs. control (OPT seed=42,
Pythia seed=1337, Pythia seed=42) -- this is the statistical confirmation
the "regularizer effect fragility" claim (Section V.B of the paper draft)
needed and did not have before this session.

## 2. A real bug found via the backfill's own sanity check

The 6 flagged Pythia mismatches were not random noise: recomputed PPL was
consistently *lower* than stored, only for configurations involving
activation quantization, by 1.9-2.75% on Pythia and (checked directly,
not assumed absent just because no warning fired) by a smaller but real
0.1-0.3% on OPT's equivalent configs. Root cause, verified by inspecting
the checkpoint's own tensors: `train_qat.py` casts the *entire* model
state_dict to FP16 for the saved checkpoint, including `FakeQuantize`'s
calibrated `scale`/`zero_point`/`min_val`/`max_val` buffers -- rounding a
value the original stored perplexity was computed without rounding.
Weight quantization (per-channel, tighter range) is barely affected;
activation quantization (a single global per-tensor scale) is affected
much more, and Pythia's fused-QKV architecture amplifies it further --
the same compounding-error-across-depth mechanism this project already
proposed to explain why Pythia's *real* activation-quantization damage is
so much worse than OPT's. This is independent corroborating evidence for
that mechanism, not just a nuisance to route around.

The bias is small and conservative (understates rather than overstates
damage), so the existing backfilled data was kept and used as-is with an
explicit caveat in the paper draft rather than requiring a redo. `train_qat.py`
was fixed the same session (keep those specific buffers at FP32 while still
casting everything else to FP16) so this cannot recur for Section B or any
future retraining.

## 3. Section C: downstream eval pipeline hardened, then launched

Two real gaps fixed in `eval_downstream.py` before running anything at
scale:
- The original `run()` wrote to `results/{model}_downstream_{strategy}.json`
  with **no seed in the filename** -- running all 3 seeds per config would
  have silently overwritten 2 of every 3 seeds' results. Refactored to use
  the project's standard `append_result()`/`results/<model>.json`
  convention (same file every other result lives in), recording seed,
  strategy, tasks, limit, and full `run_metadata()` per entry.
- Wrote `run_downstream_matrix.py`, mirroring `run_matrix.py`'s
  skip-if-done/resumable pattern, running **all 3 seeds** per config
  (not the "best seed" shortcut the plan allowed) to stay consistent with
  this project's stance against single-seed evaluation. Added a
  `MIN_REAL_LIMIT` guard so a small-`--limit` smoke test can never be
  mistaken for a completed real run (the same failure mode
  `run_matrix.py`'s `MIN_REAL_EVAL_TOKENS` check was built to prevent).

**A debugging false alarm, corrected quickly.** A `--limit 5` smoke test
piped through `| tail -60` appeared completely hung (0 bytes output,
near-zero CPU for 3+ minutes) and was killed as a suspected hang. Rerun
without the pipe and with `-u` (unbuffered): it had been doing real work
the whole time (downloading and tokenizing HellaSwag/PIQA/LAMBADA) --
Windows fully buffers a piped subprocess's stdout rather than line-
buffering it, so `tail` showed nothing until the process would have
exited. No actual bug; caught and corrected before it wasted more time.
The verified-working smoke-test entry (`limit=5`) was deleted from
`results/opt-350m.json` before launching the real matrix so it could not
be mistaken for a completed run.

The full 36-run downstream matrix (3 models x 4 configs x 3 seeds,
LAMBADA/PIQA/HellaSwag, 500-example subsample per task) ran in the
background and completed cleanly -- 36/36, zero errors, zero checkpoint
mismatches.

## 4. Section C results: one confirmation, one new finding

**Confirmatory**: Pythia-410M's activation-QAT damage, the most severe
perplexity result in this study, is not a perplexity artifact -- LAMBADA
next-word accuracy nearly halves (43.1% -> 19.1-19.5%, a -55.6% relative
drop), with PIQA/HellaSwag both down 10-14%. OPT-350M's near-zero
perplexity cost likewise shows near-zero downstream cost (all changes
within +-2%, indistinguishable from noise at this sample size). This is
independent corroboration on a completely different evaluation axis, and
it lands cleanly.

**New, not visible in perplexity alone**: on Qwen2.5-0.5B, `weights_only`
QAT -- the strategy that was cheap-to-free on both OPT and Pythia in both
perplexity and downstream terms -- costs -32.2% relative LAMBADA accuracy
and -8.6 to -9.6% on PIQA/HellaSwag, comparable in magnitude to Qwen's own
`activations_only`/`both` results. This is consistent across all 3 seeds
(no single-seed outlier driving it), so it is a separate finding from the
already-flagged `weights_only` perplexity seed-variance issue (Section
V.C), not the same anomaly showing up twice. Not yet understood: whether
this reflects a genuine RoPE/GQA weight-quantization sensitivity, a
tokenizer-specific interaction with these tasks, or something else --
added to Future Work.

Both findings, the full results table, and this new open question are
written into `docs/PAPER_DRAFT.md` §V.H, plus the Introduction, Abstract,
Limitations, and Conclusion updated to reflect Section C's completion.

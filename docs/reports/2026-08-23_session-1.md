The original study (`facebook/opt-350m`, single model, single seed) was submitted to
ACL as Submission #173. The review came back with six concrete weaknesses (no
seed variance, single model/dataset, no comparison to QLoRA/SmoothQuant/AWQ, no

that surviving material, then rebuild it from scratch and expand it into a
multi-model, multi-seed study that directly answers the reviewer's six points,
per the plan in `docs/PLAN.md`.

## 2. What was rebuilt

The entire pipeline was rewritten from scratch (no original code survived) in
`qat-research/src/`:

- `config.py` — model registry (OPT-350M, Pythia-410M, Qwen2.5-0.5B, and a
  1.1B "frontier" model), all shared hyperparameters, seeds.
- `prepare_data.py` — per-model WikiText-2 tokenization (10,000 samples, max
  512 tokens, static padding — no on-the-fly tokenization during training).
- `fakequant.py` — `FakeQuantLinear`, a wrapper around `nn.Linear` that
  preserves the original `nn.Parameter` objects (so the optimizer keeps
  working) and adds `FakeQuantize` submodules for weights and/or activations,
  selectable per the `weights_only` / `activations_only` / `both` / `none`
  strategy. Includes optional per-layer relative quantization-error logging
  (`mean_weight_rel_error`, `mean_activation_rel_error` in every result) to
  give the "activations are harder to quantize" claim a measured number, not
  just a description.
- `train_qat.py` — the QAT training loop: batch size 1, 8 gradient
  accumulation steps, `bitsandbytes.optim.AdamW8bit`, gradient checkpointing,
  500 steps, learning rate 1e-5. Saves an FP16 checkpoint per run (needed so
  downstream evaluation — Section C of the plan — evaluates the *actual
  trained weights*, not a freshly re-initialized base model).
- `eval_baseline.py` — FP16 zero-shot, INT8 dynamic (bitsandbytes), and
  SmoothQuant PTQ baselines, each independently try/except'd.
- `smoothquant_manual.py` — a from-scratch SmoothQuant implementation (see
  §3 for why the library version had to be abandoned).
- `run_matrix.py` — orchestrates all 4 trained configs x 3 seeds for one
  model, resumable (skips configs already trained for real — see §4 for a
  bug found in this exact logic).
- `qlora_frontier.py`, `eval_downstream.py`, `stats.py` — Sections B/C/D of
  the plan (memory-frontier QLoRA comparison, zero-shot downstream eval via
  `lm-eval-harness`, seed aggregation + significance testing). Built but not
  yet run this session.

## 3. What was understood — two real technical findings

### 3.1 The QAT memory-scaling rule, validated

The original chat log's informal estimate — training a model with QAT under
mixed precision costs roughly `10 x P` bytes (P = param count) before
activations — was **confirmed empirically** in this session: OPT-350M
(331.2M params) peaked at 3.6–3.9 GB during training, matching the `10 x
0.331 GB ≈ 3.31 GB` fixed-cost prediction plus ~0.3–0.6 GB of
checkpointed-activation overhead. This validated formula is what predicts a
~0.5–0.55B parameter ceiling for full QAT under a 6 GB budget — directly
motivating the "frontier" experiment (Section B of the plan) that will show
exactly where QAT must be abandoned for QLoRA-style methods instead.

### 3.2 SmoothQuant is architecture-dependent in a way that silently breaks OPT-350M

While validating the SmoothQuant PTQ baseline (requested by the ACL
reviewer), `llmcompressor`'s `SmoothQuantModifier` produced a catastrophic
perplexity (>30,000) on `facebook/opt-350m` instead of the expected
near-baseline number. Root cause, found by isolating smoothing alone (no
quantization) and confirming it alone corrupted the model:

**`facebook/opt-350m` uses post-norm** (`do_layer_norm_before=False`).
`self_attn_layer_norm` runs *after* attention+residual, so it never feeds
`q_proj`/`k_proj`/`v_proj` — those consume the raw residual stream directly.
The textbook SmoothQuant trick (fold the inverse smoothing scale into the
affine parameters of the LayerNorm immediately preceding the target Linear)
has no valid target here; the "find the preceding LN by name" heuristic used
by `llmcompressor` (and my first hand-written attempt) produces a
plausible-looking but mathematically wrong mapping, silently corrupting the
model rather than erroring.

**Fix**: rewrote SmoothQuant (`smoothquant_manual.py`) to be
architecture-agnostic — it smooths each target Linear's *own* input directly
via an explicit per-input-channel scale, with no dependency on an upstream
LayerNorm existing. This is the correct generalization the SmoothQuant paper
itself describes as a fallback for exactly this case. Verified: 47.30 PPL
(smoothed W8A8) vs 47.48 PPL (plain W8A8, no smoothing) vs 45.66 PPL (FP16) —
sane and consistent, unlike the library's ~30,000+.

A second, related bug was found and fixed in the same investigation: PyTorch's
`FakeQuantize` module defaults to having *both* its observer and its actual
fake-quantization active simultaneously. For QAT training that's correct
(the model trains through the noise from step one). For a **zero-shot PTQ**
calibration pass with no training, it's wrong — the observer's own
calibration forward passes get corrupted by fake-quantizing with the
default, uncalibrated scale (≈1.0), which rounds small-magnitude weights
(~0.02–0.05) to zero. Fixed by explicitly disabling fake-quant / enabling the
observer during calibration, then flipping both for eval — standard PTQ
protocol, but easy to get backwards when reusing a QAT-oriented module.

### 3.3 A resumability bug that could have silently corrupted the seed-averaged results

A cleanup command I ran mid-session targeted `qat-research/results` and
`qat-research/checkpoints`, but every script actually runs from
`qat-research/src/` and writes to `src/results` / `src/checkpoints` (relative
paths). The cleanup silently no-op'd on empty directories while a stale
5-step, 200-sample smoke-test checkpoint (`weights_only`, seed 42, from
earlier development) survived in the real directory. `run_matrix.py`'s
resume check only verified "does an entry for this seed exist" — it saw the
stale entry and skipped training a real 500-step run for that
(model, strategy, seed) combination.

Caught before it propagated into `activations_only` or `both`, or into
another model. Fixed by (1) purging the stale entries/checkpoint from the
correct directory, (2) hardening `already_done()` in `run_matrix.py` to
require both the correct step count *and* a minimum evaluated-token count,
so a short smoke-test run can never again be mistaken for a real one.

## 4. Known limitations hit this session

- **AWQ is unavailable on this machine.** `autoawq` requires `triton`, which
  has no published Windows wheel compatible with this Python/CUDA
  combination — `pip install autoawq` fails dependency resolution
  (`ResolutionImpossible: ... depends on triton ... no matching distributions
  ... for your environment`). SmoothQuant (own implementation, §3.2) and
  INT8 dynamic quantization stand in as the PTQ baseline family for now.
- **Full 10,000-example perplexity evaluation is expensive under FakeQuant
  overhead** — roughly 30 minutes per evaluation the first time this was
  tried, which would have meant 15–20+ hours of evaluation time alone across
  all 36 planned QAT training runs. Fixed by using a fixed, non-shuffled
  1,500-example held-out subset for the per-seed matrix sweep (statistically
  stable for perplexity; ~2–3 minutes per eval instead of ~30) while keeping
  the full 10k-example set for the one-off PTQ baselines already computed.

|---|---|---|---|---|

**Reading so far**: activations-only QAT is clearly worse than the control
and than weights-only across all 3 seeds — consistent with the original
single-seed study's direction. The original study's headline claim (weights-only
QAT *beats* the FP16 control, acting as a regularizer) does **not** clearly
hold up here — the 3-seed mean for weights-only (21.18) is marginally *worse*
than the control (21.12), the opposite of the original single-seed result.
This is exactly the kind of thing the reviewer's seed-variance critique was
meant to catch, and is being reported honestly rather than adjusted to match
the original narrative. A formal significance test (Section D of the plan)
is needed before drawing a conclusion either way — the gap is small enough
that it may not be statistically distinguishable from noise.

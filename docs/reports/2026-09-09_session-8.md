## 2. `activations_only` revealed a real, repeatable training-instability pattern -- then a full divergence

The very first `activations_only` run (seed=42) showed something never
seen on any `weights_only` or `none` run: large, sudden loss spikes (a
10-100x jump in a single step) that don't fully recover, shifting the
loss trajectory to a permanently noisier, higher baseline. Checked
immediately whether this was the same VRAM-paging noise seen elsewhere --
ruled out directly: `nvidia-smi` showed normal utilization and VRAM
(5,816 MiB, the known bounded range) at the moment of a spike, and
`weights_only`'s own logs (re-checked from this session) never exceeded
loss=5.59 across all 3 seeds, so this is specific to `activations_only`.

**Seed 42** (3 spike events, escalating toward the end of training):
step 175 (43.3), step 361 (112.8), step 428 (232.6), with the final ~20
steps (483-500) never fully recovering (staying in the 15-140 range vs.
the pre-instability ~3.3-4.3 baseline). Final result: **PPL=94.75** --
real, valid, but a ~426% increase over control (18.01), far exceeding
even Pythia-410M's "severe" activation-sensitivity case (+106%).

**Seed 1337** (spikes clustering closer together, each smaller than
seed 42's but more frequent): step 175 (43.3, coincidentally the same
step number as seed 42's first spike), step 361 (112.8), step 397 (16.1),
step 429 (61.6). Did not fully diverge, but the model was clearly damaged:
final result **PPL≈1.23×10^15** -- for all practical purposes, total
model collapse, just short of numerical infinity/NaN.

**Seed 2024** (full divergence, root-caused precisely rather than just
observed): spikes began around step 250 (226.8) and, unlike the other two
seeds, never re-stabilized -- each subsequent spike was larger than the
last in a clean, textbook unclipped-gradient-explosion pattern:

| Step | Loss |
|---|---|
| 269 | 661 |
| 273 | 3,161 |
| 276 | 1,305,584 |
| 280 | 12,457,117 |
| 284 | 11,205,642,304 |
| 286 | 2,999,978,546,803,245,056 |
| 287 | **nan** (and every step after, permanently) |

Once a NaN appears in Adam's momentum/variance state, it propagates
through every subsequent parameter update -- there is no recovery
mechanism in standard training. This was verified directly (steps 287-500
all confirmed NaN) rather than assumed. Eval on the NaN checkpoint
correctly produced `PPL=nan` (no crash -- the arithmetic just consistently
propagates NaN, exactly as expected).

## 3. Decision point: asked the user rather than deciding unilaterally

Once step 289's NaN was confirmed, continuing the remaining ~211 steps
would have cost ~4.6 more hours for zero new information (a NaN result at
step 289 guarantees a NaN result at step 500). But stopping/discarding
mid-run touches both the experimental record and real GPU time, so this
was put to the user directly rather than assumed: continue watching
(no unilateral action was taken while awaiting the answer -- the run kept
going on its own and did finish exactly as predicted, all NaN through step
500), let it run to completion, or fix the root cause and redo. Chosen:
**add gradient clipping and redo the affected runs.**

## 4. Fix: gradient clipping added, verified as a real gap not a workaround

`torch.nn.utils.clip_grad_norm_(model.parameters(), GRAD_CLIP_NORM)`
added in `train_qat.py` immediately after the 8 grad-accumulation
microbatches' `.backward()` calls, before `optimizer.step()`.
`config.GRAD_CLIP_NORM = 1.0` (the common default in LLM training, not
tuned to this data). A line is printed whenever clipping actually engages
(`grad_norm > GRAD_CLIP_NORM`), so future runs will show exactly which
steps would have spiked without it -- turning "did this help" into
something directly checkable rather than assumed. This is standard
practice essentially everywhere in LLM/QAT training; its *absence* here
was the real anomaly, not clipping's addition.

**Scope of the redo, decided deliberately, not applied blanket-wide:**
- `activations_only`: all 3 seeds cleared from `results/qwen2.5-0.5b.json`
  and their checkpoints/per-example-NLL files deleted, to be redone from
  scratch with clipping. This includes seed=42 even though it didn't fully
  diverge -- it still showed real spikes, so its result would very likely
  change under clipping, and training all 3 seeds under identical
  conditions matters for a fair comparison.
- `both` (just started, ~1 step in): will be run fresh with clipping
  enabled from the start, all 3 seeds.
- `none` and `weights_only`: **left untouched, not redone.** Neither
  strategy's logs (re-checked this session) ever showed a loss spike or
  any sign of gradient instability -- `weights_only`'s max loss across all
  3 seeds was 5.59, an order of magnitude below where clipping would
  engage. Since `clip_grad_norm_` is a no-op whenever the gradient norm is
  already under the threshold, redoing these would almost certainly
  reproduce identical numbers at the cost of real GPU time. This is a
  disclosed assumption (gradient norm wasn't logged for these
  already-completed runs, only loss), not a silently-made one.

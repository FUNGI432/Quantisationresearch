## 1. Monitor tooling had to be fixed twice before it was actually usable

The first monitor set up to track this run alerted on every step with
`step_time` in the hundreds of seconds. Given the known training-side VRAM
overshoot (steps routinely land in the 45-365s range), this fired on nearly
every step — the opposite of the "check every 10 minutes, tell me how far
we've reached" ask from earlier sessions. Replaced with a 10-minute heartbeat
loop plus a narrower immediate-alert filter (crashes, OOM, run/matrix
completion). That filter's `PPL=` term then turned out to also match the
per-batch `running_PPL=` progress lines printed every 10 eval batches,
producing ~150 pings across a single eval pass. Fixed by excluding
`running_PPL` from the alert pattern. Neither of these was a data or
science problem — just a reminder that a monitor filter needs the same
"would this fire on the failure case, and *only* the failure case" scrutiny
as the code it's watching.

## 2. `none`/seed=1337 and `none`/seed=2024 completed — but both evals ran ~20-45x slower than Day 5's fix should have allowed

| Seed | Control PPL | Peak eval VRAM | Eval time |
|---|---|---|---|
| 42 (Day 5) | 18.01 | — (pre-dates this session's fix) | ~24,925s (~6.9 hr — the original catastrophic incident) |
| 1337 | 14.02 | 5,647 MiB | 1,632s (~27 min) |
| 2024 | 14.21 | 5,649 MiB | 3,753s (~62.5 min) |

Day 5 verified `EVAL_BATCH_SIZE=1` brings eval's peak VRAM down to ~1.27 GB
and eval time down to ~80s, in an isolated fresh-process benchmark against a
saved checkpoint. Neither held up in the actual production path. Peak eval
VRAM for both real runs this session (~5.65 GB) sat almost exactly at the
6.14 GB card ceiling — clearly still in or near the same VRAM-pressure regime
the Day 5 fix was meant to eliminate.

**Root-caused, not just re-flagged, and fixed in `src/train_qat.py` and
`src/common.py`:**

1. **`evaluate_perplexity()` never wrapped its forward passes in
   `torch.no_grad()`.** Both code paths (`return_per_example=True` and the
   plain branch) built a full autograd graph on every eval batch despite
   never calling `.backward()` — wasting memory and compute on every eval
   this entire project has ever run. This is likely the dominant reason Day
   5's isolated 1.27 GB benchmark didn't match production: that benchmark
   also had this overhead, so 1.27 GB *already included* the unnecessary
   graph-building cost, meaning the "true" minimum was even lower and the
   margin against the 6 GB card was smaller than believed.
2. **The optimizer (8-bit AdamW state) and training's CUDA cache were never
   freed before eval started.** `train_qat.py` calls `evaluate_perplexity()`
   immediately after the training loop, in the same process, and only
   deleted the optimizer *after* eval finished. Eval was inheriting
   training's VRAM footprint on top of its own. Day 5's benchmark was a
   fresh process with no training memory to contend with, so this
   contribution was invisible there.

Fix: `del optimizer; gc.collect(); torch.cuda.empty_cache()` now runs
immediately after the training loop and before `evaluate_perplexity()` is
called (train_qat.py); both forward-pass branches in
`common.evaluate_perplexity()` are now wrapped in `torch.no_grad()`.
Verified via `py_compile`; **not yet verified against a real GPU run** — see
§3 for why.

## 3. Important caveat, same shape as Day 5's: the fix did not (and could not) help either run this session

`run_matrix.py` is one continuous Python process that loops through all 12
configs for a model — it does not restart the interpreter between runs.
Both `none`/seed=1337 and `none`/seed=2024 ran under the process that was
already loaded into memory before this session's fix was written, so
neither could pick it up. This was surfaced proactively (not discovered by
assuming otherwise) when the seed=2024 eval's pace matched the old,
slow behavior almost exactly. The fix will only take effect the next time
the matrix is launched as a fresh process — which happens naturally, since
this session ends with the pipeline stopped and will be resumed later.

## 4. Asked directly: is there a code bug behind the *training*-side noise too?

Investigated specifically (not just re-asserted the existing VRAM
explanation) by reading through `train_qat.py`, `fakequant.py`, and the data
pipeline (`common.py` / `prepare_data.py`) looking for a training-loop cause
independent of VRAM pressure:

- **Data loading**: ruled out. Tokenization uses fixed `padding="max_length"`
  (every example is exactly 512 tokens, pre-tokenized, memory-mapped),
  batch size 1 — no variable-shape batches, no meaningful per-step CPU cost.
- **Per-layer quantization-error tracking** (`FakeQuantLinear.track_error`):
  disabled for `strategy="none"` (`track_error = strategy != "none"`), so
  not a factor for any of this session's runs. Will add real (deliberate,
  already-documented) per-step overhead once the `weights_only` /
  `activations_only` / `both` runs start — worth watching then, not a bug.
- **Checkpoint I/O**: the resume checkpoint is a genuinely large synchronous
  write (measured directly: **2.78 GB**, full FP32 model + optimizer state,
  every `CHECKPOINT_EVERY_STEPS=10` steps). This was a real candidate, but
  cross-referencing the exact steps that follow a checkpoint save against
  the logged step times shows **no consistent spike pattern** at those
  boundaries — the big spikes (e.g. 365s at step 166 in an earlier run) land
  on non-checkpoint-aligned steps. Not ruled out as a minor contributor, but
  not the dominant cause.

Conclusion: no new training-side code bug found. The noisy 45-365s step
times remain attributed to the Day 5 diagnosis (training's VRAM peak sitting
~478 MB-1.7 GB over the 6.14 GB card, causing intermittent Windows
shared-memory paging) — external to the Python code, not fixable without
reducing the memory footprint further (e.g. a shorter sequence length),
which would change the experiment and wasn't warranted for routine noise.

## 5. Stopped deliberately at a clean run boundary, not mid-run

Per explicit instruction (the batch had been running ~18 hours across this
session and the prior one), the matrix was allowed to run to the end of the
*in-progress* run rather than killed immediately: watched for the exact
completion sequence (`PPL=` line -> `Saved per-example NLL` ->
`Saved checkpoint (FP16)`) on `none`/seed=2024, confirmed via the log, then
stopped the process. Verified after stopping:

- No `RESUME_*qwen*` checkpoint left behind (the run genuinely completed;
  nothing was killed mid-flight).
- `results/qwen2.5-0.5b.json` has all 3 `fp16_finetuned_control` (`none`)
  seed entries.
- No Python process still running (GPU fully freed).

This is the same "gracefully stop at a run boundary" pattern used in prior
sessions (e.g. stopping after Pythia's matrix finished) — safe to resume
from cold, no risk of a half-written run.

## 6. Results so far, and one open question worth flagging honestly

All 3 seeds of Qwen2.5-0.5B's `none` (FP16 fine-tuned control) configuration
are now done:

| Seed | PPL |
|---|---|
| 42 | 18.01 |
| 1337 | 14.02 |
| 2024 | 14.21 |

Mean 15.41, stdev 2.25 (~14.6% coefficient of variation) — **notably higher
seed-to-seed spread than OPT-350M or Pythia-410M ever showed** (their
configs typically varied by well under 1%). Seed=42 is the outlier (18.01
vs. ~14.1 for the other two), and it's also the seed whose training run hit
the original catastrophic VRAM-thrashing incident (peak train VRAM 9.46 GB,
~14.4 hr training time, `docs/reports/2026-08-30_session-5.md` §5-6).
Session 5 already reasoned through why that incident shouldn't have
corrupted the result (slow-but-correct arithmetic, no crash/TDR, sane loss
trajectory) — nothing here contradicts that reasoning, but the actual
seed-variance data now available is new evidence worth sitting with rather
than dismissing. It could be genuine seed variance (3 seeds is not a lot to
judge spread from) or a subtler effect of that run's anomalous conditions.
The formal Wilcoxon test (Section D) will help once more of the matrix is
in, though: **seed=42's per-example NLL was never saved**
(`per_example_nll_path` is `null` in its results.json entry — that run
predates this seed's per-example logging being wired through cleanly) and
will need the already-built-but-unrun `backfill_per_example_nll.py` before
it can participate in a paired test.

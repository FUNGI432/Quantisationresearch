## 1. A third VRAM bug, found immediately on the very first QAT-strategy run

The matrix resumed cleanly (skipped all 3 `none` seeds, started
`weights_only`/seed=42) and Day 6's eval fixes were confirmed working. But
the **first training step took 3,261.7 seconds (~54 min)** — an order of
magnitude beyond anything seen on the `none` runs (worst case 365s).
Root-caused rather than dismissed as more VRAM noise:

`FakeQuantLinear._log_error()` (used for the per-layer quantization-error
data behind `docs/MATH.md`'s compounding-error argument) called `.item()`
on every fake-quantized layer's relative error, every microbatch. For
`weights_only` that's 168 layers x 8 grad-accumulation microbatches =
**1,344 blocking CUDA syncs per step** -- versus zero for the `none`
control runs, where `track_error=False`. This is exactly why the bug was
invisible until now: it's the first run where quantization-error tracking
actually turned on. Combined with training already sitting at the edge of
the 6.14 GB card, each sync was a chance to stall on Windows' shared-memory
paging fallback -- 1,344 chances per step instead of the ~8 already baked
into the loss-logging path.

**Fixed** (`src/fakequant.py`, `src/train_qat.py`): `_log_error` now stores
the error as a GPU tensor (`.detach()`, no sync) instead of calling
`.item()` immediately. A new `FakeQuantLinear.flush_error_log()` converts
that step's entries to plain floats once, right after `optimizer.step()`
-- deliberately once per step, not once for the whole run, since keeping
every tensor alive for all 500 steps (up to ~672,000 of them) would add
real VRAM pressure back on a card already at its ceiling (PyTorch's CUDA
allocator rounds even a 4-byte scalar up to a minimum block size).

**Verified before trusting it**, not just reasoned about: killed the
in-flight run (safe -- no resume checkpoint existed yet this early),
applied the fix, relaunched, and watched step-by-step. Step 1: 10.3s. Step
2: 22.2s. Confirmed.

## 2. A second bug found the same way, on the very next resume

Later in the session, the pipeline was stopped and resumed again (user
needed the GPU for something else). On resume, `VRAM after setup` printed
**5,696 MiB** -- versus **1,885 MiB** on this exact run's original fresh
start. Steps immediately slowed back to 251-372s.

Root cause: `train_qat.py`'s resume path does
`ckpt = torch.load(resume_path, map_location=DEVICE)`, loading the entire
checkpoint (full FP32 model + optimizer state, ~2.78 GB) onto the GPU, then
copies its contents into the live model/optimizer via `load_state_dict()`
-- but `ckpt` itself was never freed. It sat in VRAM as a redundant full
second copy for the rest of the run. The ~3.8 GB gap between the two "VRAM
after setup" numbers matches the checkpoint's size almost exactly.

**Fixed**: `del ckpt; gc.collect(); torch.cuda.empty_cache()` right after
the state dicts are loaded. **Verified**: VRAM after setup dropped to
2,848 MiB (the residual gap vs. 1,885 MiB is expected, not a bug -- a
resumed run's optimizer already has its real 8-bit AdamW state populated
at that print point; a fresh run's optimizer is still empty until its
first `.step()`). First post-resume step: 67.3s, back in the known noise
band. This fix benefits every future resume in the project, not just this
one.

## 3. A bug I introduced while fixing bug #1, caught before it cost real time

`train_qat.py`'s post-training error-summary code still called `.item()`
on every value in `FakeQuantLinear.error_log`, expecting GPU tensors -- but
`flush_error_log()` (added for bug #1) already converts everything to
plain floats every step. `weights_only`/seed=42 crashed with
`AttributeError: 'float' object has no attribute 'item'` right after
finishing all 500 training steps (12,141s of training, complete and
undamaged). Fixed with a small `isinstance` guard so the conversion is a
no-op when values are already floats. Verified the run then completed
cleanly through eval and checkpoint save on the retry.

**Important side effect, discovered while investigating**: because the
crash happened after training finished but before eval ran, and the
resume checkpoint was saved at exactly step 500, resuming after the fix
skipped the training loop entirely (`range(500, 500)` is empty) -- which
means `FakeQuantLinear.error_log` was never repopulated on the successful
retry. **`weights_only`/seed=42's `mean_weight_rel_error` is `null`** in
its results.json entry as a result. This is a real, permanent, minor data
gap for this one run specifically (not recoverable without a full
retrain -- unlike per-example NLL, per-layer quantization error can only be
observed during the actual forward passes of training, not reconstructed
from a final checkpoint). PPL and per-example NLL, which come from eval
(which did run, both times), are unaffected. Noting this explicitly rather
than letting it surface later as an unexplained missing value.

**Notable, unresolved**: seed=1337's PPL (28.91) is dramatically worse than
seed=42's (18.69) for the *same* `weights_only` strategy -- and worse than

explanations not yet distinguished: genuine seed variance specific to this
architecture, training instability specifically in the seed=1337 run
(worth checking its full loss trajectory, not just the final numbers), or
an artifact of seed=1337's much higher peak VRAM (6,625 MiB, itself above
the 6.14 GB card) interacting badly with the quantization noise somehow.

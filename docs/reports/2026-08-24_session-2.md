## 2. What was understood — findings and issues this session

### 2.1 A genuinely strong new finding: activation-quantization sensitivity is architecture-dependent, not universal

This is the headline result of the session. Both models now have complete
4-seed-averaged data:

| Configuration | OPT-350M | Pythia-410M |
|---|---|---|
| FP16 fine-tuned control | 21.12 | 16.75 |
| QAT weights-only | 21.18 (+0.3%) | 16.82 (+0.4%) |
| QAT activations-only | 21.82 (+3.3%) | **34.54 (+106%)** |
| QAT both | 21.92 (+3.8%) | 34.58 (+106%) |

Weights-only QAT behaves almost identically on both architectures — a small,
consistent, near-negligible degradation. **Activation quantization is where
the two architectures diverge sharply**: a mild 3.3% hit on OPT-350M versus
more than doubling perplexity on Pythia-410M. The leading hypothesis is
Pythia's fused QKV projection (GPT-NeoX style, one combined Linear producing
query+key+value) versus OPT's three separate q/k/v projections — a fused
projection's output activations may carry a much wider/more heterogeneous
dynamic range (three different downstream uses folded into one tensor),
making it harder for a single per-tensor quantization scale to fit well.
This is not yet verified beyond the perplexity numbers — the per-layer
`mean_activation_rel_error` already logged in `results/*.json` for every run
should be checked next to see if it's quantitatively higher for Pythia's
fused layer specifically, which would substantiate the hypothesis directly
rather than just via its downstream effect on perplexity.

This is exactly the kind of result the original single-model v1 study had no
way to produce, and directly strengthens the response to the ACL reviewer's
"does this generalize" critique — the answer turns out to be genuinely
interesting (no, not uniformly, and here's a concrete architectural reason
why) rather than a simple yes/no.

### 2.2 A recurring, unexplained eval-time anomaly on Pythia-410M

Several runs took far longer than every other run of the identical
configuration, with no difference in correctness (perplexity always landed
in the expected range) or code path:

| Run | Expected eval time | Actual eval time |
|---|---|---|
| `weights_only`/seed=42 | ~150-200s | 2,566s (~13x) |
| `both`/seed=1337 | ~150-200s | 7,528s (~40x) |
| `both`/seed=2024 | ~150-200s | 3,443s (~18x) |

Notably, `both`/seed=42 (the first `both` run) evaluated in a normal 210s —
so it isn't that the `both` strategy is inherently slower, since two of the
three `both` seeds were fast and one was extremely slow. This rules out a
simple "this strategy's code path is slow" explanation. Not yet root-caused;
current best guess is background system contention (Windows disk indexing,
updates, or other processes competing for CPU/disk during data loading)
rather than a bug in the pipeline itself, but this is unconfirmed. Flagged
in the README's Known Issues rather than silently averaged away — it doesn't
affect the perplexity results, only wall-clock time, but a 40x slowdown on
an unpredictable subset of runs is a real problem for time-budgeting future
sessions (see §4).
